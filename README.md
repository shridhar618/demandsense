# DemandSense AI — Phases 1–3: Ingestion, Forecasting, Decision & Inventory Intelligence

![Python](https://img.shields.io/badge/Python-3776AB?logo=python&logoColor=white) ![FastAPI](https://img.shields.io/badge/FastAPI-009688?logo=fastapi&logoColor=white) ![React](https://img.shields.io/badge/React-20232A?logo=react&logoColor=white)

*Predict. Explain. Optimize. Decide.*

Three working vertical slices: getting demand history in cleanly, turning it
into trustworthy forecasts, turning forecasts into per-product reorder
decisions, and now a catalog-wide inventory intelligence view (ABC analysis,
movement classification, dead stock, stockout/overstock risk).

## What's actually working right now

- **CSV upload** with real validation, deduplication, and missing-value
  interpolation.
- **Two forecasting models trained and compared automatically**: Prophet and
  XGBoost, with held-out MAE/RMSE/MAPE and XGBoost feature importance.
- **Inventory snapshot upload**: on-hand stock, unit cost, lead time, order
  cost, holding cost per product.
- **Decision Intelligence**: forecast + inventory → a recommendation
  (Purchase Immediately / Increase / Reduce / Monitor) using real formulas
  (EOQ, safety stock, reorder point), with reasoning, confidence, priority,
  risk, and estimated financial impact.
- **Inventory Intelligence** (new): a second dashboard page —
  - **ABC classification**: Pareto analysis on trailing revenue (A = top 80%
    cumulative revenue, B = next 15%, C = remaining 5%)
  - **Movement classification**: fast/medium/slow based on annualized
    turnover ratio
  - **Dead stock detection**: on-hand stock with zero demand in the last 30
    days
  - **Stockout risk / overstock flags**: days-of-cover vs. supplier lead
    time, computed catalog-wide
  - KPI cards + ABC/movement breakdown charts + a full sortable product
    table with all flags
- A dashboard where you upload demand + inventory data, pick a product,
  train, view the forecast, and generate a recommendation — all against a
  live backend, nothing mocked.

## What's *not* built yet

Procurement (supplier ranking, PO generation), the AI copilot, what-if
simulation, RBAC, Kafka streaming. The nav sidebar shows those sections
marked "soon."

## Running locally (fastest path)

### Backend

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# Prophet needs a compiled CmdStan toolchain. One-time setup:
python -m cmdstanpy.install_cmdstan --cores 4
export CMDSTAN=~/.cmdstan/cmdstan-2.39.0

# The prophet wheel ships a broken bundled CmdStan reference; remove it so
# prophet falls back to the CMDSTAN path above (see app/ml/prophet_model.py
# for details — this is handled automatically, this note is just FYI):
rm -rf .venv/lib/python*/site-packages/prophet/stan_model/cmdstan-2.33.1

uvicorn app.main:app --reload --port 8000
```

API docs at `http://localhost:8000/docs` (Swagger, auto-generated by FastAPI).

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. The Vite dev server proxies `/api/*` to the
backend on port 8000 — see `vite.config.ts`.

### Try it

Two synthetic sample files are included:
- `sample_demand.csv` — two products, 18 months of daily history, with
  intentional data-quality issues (a duplicate row, missing days, outliers)
  so you can see the cleaning pipeline actually work.
- `sample_inventory.csv` — current stock levels for both products, tuned so
  one triggers a "Purchase Immediately" recommendation (low stock, long
  lead time) and the other triggers "Reduce Inventory" (overstocked).

Upload both, select a product, click "Train forecast models," then
"Generate recommendation."

## Design notes

The visual direction draws from Stripe/Linear/Datadog/Palantir rather than a
generic admin-template look: a graphite (not pure black) canvas, a warm
amber "signal" accent standing in for forecasts/decisions, a cool cyan
counter-accent for actual-vs-predicted comparison, Space Grotesk for
display type, and IBM Plex Mono for all numeric readouts so metrics read as
instrumented data rather than decoration. Dark mode is default; light mode
is fully themed via CSS custom properties (`src/index.css`), toggle in the
top bar.

## Data format expected

**Demand history CSV:**

| column | required | notes |
|---|---|---|
| `date` | yes | any parseable date format |
| `product_sku` | yes | product identifier |
| `quantity` | yes | numeric demand quantity |
| `product_name` | no | defaults to SKU |
| `category` | no | defaults to "Uncategorized" |
| `warehouse` | no | defaults to "DEFAULT" |
| `revenue` | no | |

**Inventory levels CSV** (upload demand history first — SKUs must already exist):

| column | required | notes |
|---|---|---|
| `product_sku` | yes | must match a product from a demand upload |
| `on_hand_quantity` | yes | current stock on hand |
| `warehouse` | no | defaults to "DEFAULT" |
| `unit_cost` | no | defaults to 0 |
| `lead_time_days` | no | supplier lead time, defaults to 7 |
| `order_cost` | no | fixed cost per purchase order, defaults to 50 |
| `holding_cost_pct` | no | annual holding cost as a fraction of unit cost, defaults to 0.20 |

## Decision Intelligence formulas

These are standard inventory-management formulas, not a black box:

- **Safety stock** = z × σ(daily demand) × √(lead time days), where z is the
  service-level factor (default 1.65 ≈ 95% service level)
- **Reorder point** = avg daily demand × lead time days + safety stock
- **Economic Order Quantity (EOQ)** = √(2 × annual demand × order cost ÷
  holding cost per unit) — the classic Wilson formula
- **Days of cover** = on-hand stock ÷ forecasted daily demand rate (forward-
  looking, not historical average — the whole point of forecasting first)
- **Confidence** on the recommendation is derived from the forecasting
  model's own held-out MAPE — a recommendation built on a less accurate
  forecast is flagged as less confident, not presented with false certainty

## Known limitations of this phase

- Forecasts and recommendations aggregate across warehouses into one series
  per product (no per-warehouse granularity yet).
- No auth/RBAC yet — this phase is single-tenant, no login.
- XGBoost's confidence band is a first-order approximation (residual std
  widened by horizon distance), not a proper quantile-regression interval.
  Prophet's interval is a real Bayesian credible interval from the model.
- Retraining and recommendation generation are on-demand (button click), not
  scheduled/automatic yet.
- The "estimated savings" figures use unit cost as a proxy for revenue
  impact since no separate selling-price field exists yet — treat these as
  directional, not exact P&L numbers.

## Suggested next phase

- **Procurement** (supplier ranking, purchase order generation) — the
  "Purchase Immediately" recommendations and stockout-risk flags from these
  phases are natural triggers for a generated purchase order once supplier
  data exists.
- **Warehouse comparison** — the inventory intelligence data model already
  carries a `warehouse` field; multi-warehouse aggregation/comparison is a
  straightforward extension once sample data spans more than one warehouse.
- **What-If Simulation** — since forecasting, decisions, and inventory
  intelligence are all real, formula-driven pipelines now, they're
  straightforward to re-run with perturbed inputs (e.g. +20% demand shock,
  a 10-day supplier delay) to see the cascading effect on recommendations.
